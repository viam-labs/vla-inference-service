# `action_space: "delta-ee"` — running an EVO1 checkpoint on end-effector pose deltas

Date: 2026-08-27
Status: design approved, implemented
Dataset contract: `viam-labs/viam-sequence-to-lerobot` PR #2, branch
`action-space-delta-ee` (`eaa1937`)
Reference checkpoint dataset: `viamrobotics/xarm-open-box-eedelta` — 125 episodes,
34,670 frames, 10 fps, xArm

## Motivation

Every checkpoint this module can run today speaks joint angles. The controller
reads `get_joint_positions()`, selects `state_joint_indices`, converts degrees to
the checkpoint's unit, and writes the policy's absolute output back with
`move_to_joint_positions`.

An EVO1 checkpoint trained on `xarm-open-box-eedelta` speaks something else
entirely: it observes the **tool pose** and emits a **relative pose delta**. There
is no joint vector anywhere in that loop, so no amount of configuring the existing
path reaches it — `state_joint_indices` has nothing to index, the 9-dim
observation is not a joint selection, and the 6-dim action is not a position.

## The dataset contract

Fixed by the converter, not by this module. Both widths are constants here, not
config.

`observation.state`, 9 dims:

| slot | meaning |
| --- | --- |
| 0–2 | `x, y, z` in **millimetres**, exactly as Viam's `EndPosition` reports them |
| 3–8 | the first two **ROWS** of the pose's 3×3 rotation matrix, row-major |

The third row is recoverable by cross product, which is why only two are stored.
Rows rather than a three-number encoding because the arm holds its tool
near-vertical, where the rotation angle sits within 0.03 rad of π — exactly where
an axis-angle *state* flips sign under physically smooth motion. A rotation matrix
varies smoothly everywhere in SO(3); no three-number encoding does.

`action`, 6 dims: `[dx, dy, dz]` in millimetres, then `[drx, dry, drz]` — the
**body-frame** relative rotation `R_t⁻¹ · R_t+1` as an axis-angle vector in
radians. Three numbers are safe *here* because per-tick rotations are ~0.014 rad,
two orders of magnitude clear of the branch cut at π, and better conditioned than
matrix rows whose diagonal would be pinned at 1.

**No gripper channel.** The recording captured only the xarm's `EndPosition` and
its six `JointPositions`. There was no gripper component and no seventh joint, so
the policy cannot command jaw aperture. Jaws stay on the existing do-command
path, out of band.

## Two ways to get this silently wrong

Both produce a rotation that is valid, moves the arm smoothly, and is wrong.
Neither has a runtime symptom.

1. **Transposing.** The state holds matrix *rows*. Reading them as columns yields
   a different, equally well-formed rotation. Measured on the recorded poses, rows
   and columns differ by 0.047–0.06 — small enough to look like noise, far too
   large to be it.
2. **Left-multiplying the delta.** `dR · R_t` applies the rotation in the world
   frame; the dataset's action is body-frame, `R_t · dR`. The tool still moves
   smoothly, just about the wrong axes.

A third, subtler one lives inside the orientation-vector decode: scipy orders a
quaternion `(x, y, z, w)` and the Viam SDK `(w, i, j, k)`. Reordering by hand
produces a plausible wrong rotation with nothing to catch it.

`tests/controller/test_pose.py` carries a canary for each. Each was verified by
introducing the mistake in `src/vla/controller/pose.py` and confirming the suite
fails — see the PR body for the output.

## 1. Vendoring the pose helpers

`src/vla/controller/pose.py` is a **verbatim copy** of the converter's
`src/viam_sequence_to_lerobot/pose.py` at `eaa1937`, with a provenance block
prepended to the module docstring and nothing below it changed.

Copied rather than depended on, for two reasons:

- The converter's package declares `lerobot>=0.4` and `pyarrow>=14`. An inference
  module that must `uv pip install` on a robot has no business carrying a
  dataset-building toolchain, and there is no extras split that would let it
  avoid one.
- The only version of these helpers matching the deployed checkpoints lives on an
  **unmerged branch**. A `git+https://…@action-space-delta-ee` dependency pins
  this module to a ref that can be force-pushed or deleted out from under it.

The copy is only worth as much as the thing proving it is still a copy, so
`tests/controller/test_pose.py` asserts against golden vectors generated by
*executing the converter file*, and the test docstring records how to regenerate
them. At vendoring time `pose_state` and `state_compose` were confirmed
bit-identical (`np.array_equal`) to the converter's own output across three poses
and three deltas.

`scipy>=1.11` becomes a **core** dependency, not part of the `lerobot` extra: the
controller runs the composition itself and can be deployed on a machine that never
loads a checkpoint.

**Rejected: reimplementing the rotation math on numpy** to avoid the scipy
dependency. `state_rotation`'s Gram-Schmidt, `Rotation.from_matrix`'s
orthogonalisation, and the rotvec/matrix conversions are exactly the code whose
divergence from the converter would be invisible.

## 2. Config surface

One new field on the existing `ControllerConfig`. Everything else in this section
follows from it.

```json
{
  "action_space": "delta-ee",
  "policy_service": "vla-policy",
  "arm": "xarm",
  "cameras": { "observation.images.top": "cam-top" },
  "fps": 10.0
}
```

| Field | Values | Default | Notes |
| --- | --- | --- | --- |
| `action_space` | `joints` \| `delta-ee` | `"joints"` | `joints` is the deployed path and unchanged. |
| `state_units` | object | `{"translation": "millimeters", "rotation": "unitless"}` | Per-segment; see §3. |
| `action_units` | object | `{"translation": "millimeters", "rotation": "radians"}` | Per-segment; see §3. |
| `image_fit` | as before | `"stretch_bicubic"` | Different default, see §5. |
| `safety.max_tcp_delta_mm` | number | `40.0` | Per-tick translation ceiling; see §6. |
| `safety.max_tcp_rot_delta_rads` | number | `0.12` | Per-tick rotation ceiling. |
| `safety.max_tcp_vel_mms_per_sec` | number | — | Operator-facing knob; the ceiling is derived as `vel / fps`. |
| `safety.max_tcp_rot_vel_rads_per_sec` | number | — | Same, for rotation. |

### Three things it *rejects* rather than ignores

Each would be inert on this path, and an inert safety limit or an inert state
layout is precisely the config an operator assumes is in force.

| Rejected under `delta-ee` | Why |
| --- | --- |
| `state_joint_indices` | The observation comes from `EndPosition`. The field describes a state layout that no longer exists. |
| `gripper.type != "none"` | No gripper channel in the action space. Accepting one would make `_check_action_dim` demand a 7th dimension the policy never emits. |
| `safety.max_joint_delta_degs`, `max_start_delta_degs`, `max_vel_degs_per_sec`, `joint_limits_degs` | No enforcement path on `move_to_position`. |

Rejection is **symmetric**: the four `max_tcp_*` keys are refused under
`"joints"` for the same reason.

## 3. Per-segment units

The joints path's `from_degrees`/`to_degrees` take a single unit string, which
works because a joint vector is one quantity end to end. A delta-EE vector is not:
the state is 3 lengths plus 6 dimensionless numbers, the action is 3 lengths plus
3 angles. One string cannot describe either, and silently applying `"radians"` to
the whole action is how a translation in millimetres gets multiplied by π/180.

`units.py` gains a run-length-encoded `VectorUnits` — a tuple of
`UnitSegment(size, unit)` — plus `to_working`/`from_working`. The existing
degrees pair is untouched.

**Working units are fixed per quantity kind, not configurable:**

| kind | working unit | because |
| --- | --- | --- |
| length | millimetres | `viam.proto.common.Pose` carries mm, and the dataset stored `EndPosition` mm verbatim |
| angle | radians | the rotation segment is consumed by `Rotation.from_rotvec`, and the Cartesian clamp is in radians |
| dimensionless | itself | |

Note the angle basis here is radians while `from_degrees`/`to_degrees` are
degrees-based. That is not an inconsistency to tidy away: a joint angle is a Viam
quantity (`JointPositions` is degrees) and an axis-angle rotation vector is not a
Viam quantity at all. Forcing the rotvec through degrees would make `radians` —
the overwhelmingly common case, and the one the converter emits — a lossy
`deg2rad(rad2deg(x))` round trip on a vector about to become arm motion.

The state's rotation segment is pinned to `"unitless"` as a **one-choice field**
rather than hidden, so an operator who writes `"radians"` there is told it is
wrong instead of having it quietly ignored.

**Rejected: a single `state_scale`/`action_scale` multiplier.** It cannot express
"millimetres here, radians there" without the operator computing the ratio, and a
wrong ratio is invisible.

## 4. Observation

`ObservationBuilder` gains an `action_space` parameter and branches in exactly one
place: which arm coroutine goes into the existing `asyncio.gather`, and how the
result becomes a state. The camera half is byte-identical.

```
joints:    get_joint_positions()  -> select indices -> from_degrees   -> N-vector
delta-ee:  get_end_position()     -> pose_state()   -> from_working   -> 9-vector
```

The gather shape does not change — one arm read either way — so the tick's latency
profile is the same. The gripper read is naturally absent because `gripper.type`
is forced to `"none"`.

`pose_state` is called with the payload shape it was written against
(`{"pose": {...}}`, the export JSON), so the vendored file needs no adapter of its
own. The protobuf `Pose` carries exactly those seven fields with `theta` in
degrees, and `get_end_position()` returns the same message the recording captured.

A zero-length orientation vector, a non-`Pose` return, and a failing read each
surface as an `ObservationError` naming the arm call, matching how every other
read failure in that module is reported.

## 5. Image preprocessing

**Verified against the pinned lerobot, not assumed.** `_batched_resize_01`
(`lerobot/policies/evo1/internvl3_embedder.py`, at the pinned
`ff7cc3de1de830f5f3276918a013d04bdf9ea4be`) resizes straight to
`(image_size, image_size)` — default 448 — with `InterpolationMode.BICUBIC` and
`antialias=True`. Its own docstring states it exists to mirror InternVL3's
reference PIL preprocessing (`to_pil_image` → `Image.resize` → `to_tensor`).
**EVO1 does not pad.**

That makes `"pad"` the wrong default here. smolvla's `resize_with_pad` runs on the
dataset frame at train time, so a controller-side pad reproduces the geometry
training saw. EVO1 squashes the *unpadded* dataset frame to a square, so a
controller-side pad would feed it black bars that then get squashed along with
the picture — bars no training frame ever had.

**`"stretch"` was checked, not assumed, and is not equivalent.** It uses
`Image.BILINEAR`. Measured against `_batched_resize_01` on random frames:

| controller fit | mean abs difference from EVO1's resize |
| --- | --- |
| PIL `BICUBIC` | 0.13–0.29 / 255 |
| PIL `BILINEAR` (`"stretch"`) | 3.3–13.1 / 255 |

An order of magnitude apart, so a third fit earns its place. `"stretch"` keeps its
exact current behaviour — an existing deployment must be able to reproduce its
output byte-for-byte — and `IMAGE_FITS` gains `"stretch_bicubic"`: the same
geometry, EVO1's resampler.

Both halves of that comparison are pinned in
`tests/controller/test_observation_differential.py` (marker: `differential`),
including the assertion that BILINEAR would *not* have passed — without it the
tolerance could loosen to accept any resampler at all.

Worth stating plainly: the controller resizes onto the checkpoint's **declared**
feature shape, not onto 448. When the live camera already matches that shape,
`_encode` does nothing and parity is exact — which is the case a real deployment
should be in. The resampler only matters when it does not.

## 6. Safety

`move_to_position` carries no notion of "this delta represents one 100 ms tick".
It takes a pose and drives to it at whatever speed the driver chooses. So an
out-of-distribution delta would be executed at full driver speed, and bounding
the delta is the only thing between a bad chunk and a fast, large tool motion —
exactly the role `max_joint_delta_degs` plays on the joints path.

`CartesianSafetyLayer` applies two per-tick magnitude ceilings:
`norm(delta[:3])` in mm and `norm(delta[3:])` in radians. Defaults from the
recorded per-tick statistics:

| quantity | median | p99 | max | default |
| --- | --- | --- | --- | --- |
| translation | 9.31 mm | 28.40 mm | 96.83 mm | 40 mm |
| rotation | 0.0142 rad | 0.0807 rad | 0.3246 rad | 0.12 rad |

Each sits ~1.4× above the p99 so in-distribution motion never clamps and
`clamp_counts` stays a real signal, and below the largest single tick in the
recording — which at 10 fps would be 968 mm/s of tool travel. Clamping below the
observed maximum is the deliberate half: those extremes are a handful of frames
out of 34,670, and a policy emitting one every tick is out of distribution rather
than in a hurry.

Operator-facing knobs are **velocities** (`max_tcp_vel_mms_per_sec`,
`max_tcp_rot_vel_rads_per_sec`), with the per-tick ceiling derived as `vel / fps`
and a refusal if both are given and disagree — the same rule, and now literally
the same helper, as `max_joint_delta_degs`. `reconfigure()` logs the ceiling and
the tool speed it implies, because `move_to_position` accepts no speed argument
and the log is the only place an operator can read it off.

**Both clamps scale the whole 3-vector by one factor rather than clipping
component-wise.** Component-wise clipping changes the *direction* of the motion:
`(100, 10, 0)` would clip to `(40, 10, 0)`, a different heading than the policy
asked for, and one that varies with how far over the ceiling the step was. In
joint space that reshaping is the definition of a per-joint limit; in Cartesian
space the direction is the tool's physical path, so "same way, less far" is the
only clamp that means anything. Same argument for the rotation vector, where the
norm is the angle and the direction is the axis.

**No start-delta clamp.** A delta-EE action is already a delta, so the first
tick's magnitude is the same quantity every later tick's clamp measures. A second
threshold on it would be the same check under a second name.

**Joint limits.** `joint_limits_degs` has no Cartesian analogue. Out-of-range and
unreachable targets are refused by the arm driver's own inverse kinematics rather
than by this service. Note `move_to_position` is the arm *component* method, not
the motion service, so there is no obstacle avoidance on this path either.

## 7. Arm write

```
delta        = to_working(action, action_units)          # -> mm, radians
safe         = CartesianSafetyLayer.apply(delta)
current      = pose_state(await arm.get_end_position())  # freshly measured
target       = state_compose(current, safe)              # rows; RIGHT-multiply
vector       = orientation_vector(state_rotation(target))
await arm.move_to_position(Pose(x, y, z, **vector))
```

Composed against the **measured** pose, re-read every tick, for the same reason
the joints path clamps against measured joints: an arm lagging its setpoint must
not have deltas accumulate on top of a position it never reached.

`state_compose` is called, never reimplemented. It is the single place both
failure modes from the top of this document are foreclosed.

### A `move_to_position` refusal is bounded, not fatal

This is the one place the delta-EE path departs from "arm command failures are
unconditionally fatal", and the departure is specific.

The joints path's target is the measured position plus a small clamped delta, so
it is always inside joint space; a refusal there means hardware trouble. This call
additionally runs the driver's **inverse kinematics**, which can decline a
kinematically unreachable pose or a singularity while the hardware is perfectly
healthy — and declines *before* commanding motion, so the arm is stationary and
safe. That failure class simply does not exist on the joints path.

Because the action is relative, skipping the tick self-heals: the next tick
re-reads the measured pose and composes a fresh delta onto it. Consecutive
refusals are bounded by the existing `starvation_grace_ticks` (4 ticks, 400 ms at
10 fps, by default) — the same shape as the starvation bound, and not gated by
`stop_on_error`, because the arm never moved. A genuinely stuck arm still halts
promptly.

## 8. Checkpoint validation

`_check_action_dim` branches to a straight equality check: `action_dim == 6` and
`state_dim == 9`. Not the negotiation the joints path performs, because both
widths are fixed by the dataset contract.

It earns its place because every mistake it prevents is silent. A 7-dim action
would have its extra channel dropped by `state_compose`'s slicing; a state of the
wrong width would be Gram-Schmidt'd out of whatever six numbers happened to land
in `state[3:9]`. Both produce arm motion.

`_check_end_position` is the delta-EE counterpart of `_check_joint_indices`: it
runs the full decode at `_run()` setup, before any motion, so an arm that does not
implement `get_end_position` — or returns a degenerate orientation vector — fails
at `start` rather than on the first tick after the loop reports `running`.

### EVO1 loads

Confirmed against the pinned extra rather than assumed: `get_policy_class("evo1")`
resolves to `Evo1Policy`, `Evo1Config().image_resolution == (448, 448)`,
`max_action_dim == 24`. `src/vla/policy/` needs no changes — the padded 24-wide
chunk is cropped to the checkpoint's real action dim by
`Evo1ActionProcessorStep`, which `LeRobotBackend.predict_chunk` already routes
through as `processed`.

## What is shared, and deliberately so

The scheduler, `ActionQueue`, chunk pacing, starvation bounds, `status`
reporting, `stop_on_error` semantics, RTC/async mode resolution, camera reads,
and image encoding are all common. `action_space` branches in five places
(`config.parse`, `ObservationBuilder.build`, `_build_safety`,
`_check_action_dim`, and the loop's actuation call) and nowhere else.

`clamp_counts` is keyed the same way in both layers, so `status` reports the two
identically and an operator's dashboard needs no branch.

## Testing

`tests/controller/test_pose.py` (new) — golden vectors from the converter; the
compose/delta inverse property; the transpose canary; the left-multiply canary;
the quaternion-order guard. The two canaries assert both that production matches
the correct answer *and* that it does not match the mistaken one, and each was
verified by making the mistake.

`test_units.py` — per-segment conversion, the mm/rad identity case, unitless
segments never scaled, width mismatch refused rather than broadcast.

`test_safety.py` — in-distribution and p99 deltas passing untouched, the recorded
maximum clamping, direction preservation asserted against what `np.clip` would
have produced, independent translation/rotation clamping, boundary equality.

`test_config.py` — every rejection above, in both directions; and
`test_an_existing_joints_config_is_unaffected_in_every_field`, which spells out
each default by value rather than comparing against a golden built from the same
code.

`test_observation.py` — the 9-dim build from a known pose, the transpose canary
at the observation boundary, no joint read on this path, per-segment units, the
three refusal paths, and the three `image_fit` properties.

`test_observation_differential.py` (marker `differential`) — `stretch_bicubic`
against EVO1's actual resize, and the counter-test that BILINEAR fails the same
threshold.

`test_service.py` — `move_to_position` used and `move_to_joint_positions` never;
zero-delta round trip through the controller's own code path; ticks compounding;
the Cartesian clamp firing end to end; per-segment units end to end; the four
pre-motion refusals; and the three refusal-handling behaviours.

## Explicitly out of scope

**Solving IK locally and reusing `move_to_joint_positions`.** Considered; the
owner chose `move_to_position`. It would have brought `joint_limits_degs` and the
joint delta clamp back into force, at the cost of this module owning a kinematic
model per arm.

**A gripper channel.** Not in the dataset, so not in the action space.

**`mode: "rtc"`.** Unchanged and still unimplemented, for both action spaces.
